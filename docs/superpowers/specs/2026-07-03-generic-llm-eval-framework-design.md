# Generic LLM Evaluation Framework — Design Spec

**Date:** 2026-07-03
**Author:** Vaishnavi Darandale (QA Architect)
**Status:** Draft — Awaiting Implementation Plan
**Replaces:** Tightly-coupled `csa-llm-evaluation` (summary/topics/insights APIs only)

---

## 1. Problem Statement

The current `csa-llm-evaluation` framework evaluates three specific CXOne agentic analytics APIs (summary, topics, insights-recommendations). Rules S1–S16 and R1–R16 are hardcoded to those API response shapes. As NICE expands LLM-generated content to knowledge articles, mail generation, action history, topic categories, and beyond, a new framework is needed that:

- Works for **any LLM-generated API output** without code changes
- Allows QA engineers to plug in a **Swagger doc + Epic + Test Cases** and get a working evaluation suite
- Automatically classifies rules into **3 layers** (deterministic, LLM-as-judge, RAGAS) using an agent
- Supports **multiple LLM judge models** (Bedrock, OpenAI, Azure, local)
- Accepts **ground truth from any source** — REST API, SQL, DynamoDB, static fixtures, or none
- Supports **live API calls and static replay** (capture + replay mode)

---

## 2. Goals & Non-Goals

### Goals
- Zero rule-writing for end users — rules are generated by an agent from the epic
- Human review gate: generated rules saved as reviewable YAML before execution
- Flexible pipeline: scenarios can chain multiple ground truth sources + one target API
- Pack model: every evaluation domain is a self-contained, versioned folder
- Multi-model: per-rule model selection + optional comparison mode
- CLI-driven: `llmeval generate`, `llmeval run`, `llmeval capture`
- Backwards compatible output: ReportPortal, Confluence, JSON, HTML

### Non-Goals
- Real-time / streaming evaluation (batch evaluation only)
- Automated remediation of failing outputs
- Shared central service / SaaS deployment (deferred — teams use the library in their own CI)
- Training or fine-tuning models based on eval results

## 3. Core Concepts

### 3.1 Eval Pack

The **unit of work**. A self-contained folder describing how to evaluate one LLM output domain (e.g. knowledge articles, mail generation). Versioned in git. Portable across teams.

```
eval-packs/
└── knowledge-article/
    ├── pack.yaml                     # Pack identity, version, owner
    ├── swagger/
    │   ├── knowledge-api.yaml        # Target API (LLM output source)
    │   └── topics-api.yaml           # Context API (optional)
    ├── epics/
    │   └── KA-001-article-gen.md     # Epic + acceptance criteria (plain markdown)
    ├── testcases/
    │   └── scenarios.yaml            # Input scenarios + expected behaviors
    ├── ground_truth/
    │   ├── sources.yaml              # Ground truth provider config
    │   └── fixtures/
    │       └── topics_response.json  # Captured or hand-written static data
    ├── generated/
    │   └── layers.yaml               # AUTO-GENERATED by Rule Agent — do not edit
    ├── overrides/
    │   └── layers_override.yaml      # Human edits that survive regeneration
    └── models.yaml                   # Model selection per layer
```

**pack.yaml**
```yaml
name: knowledge-article-evaluation
version: 1.2.0
owner: qa-platform@nice.com
target_api: swagger/knowledge-api.yaml
context_apis:
  - swagger/topics-api.yaml
```

### 3.2 Scenario

A single evaluation run defined in `testcases/scenarios.yaml`. Declares:
- The inputs to send to the target API
- Which ground truth sources to resolve
- Whether to run live or replay from fixtures

```yaml
scenarios:
  - id: routing_article
    description: "Generate article about IVR routing"
    mode: live                          # live | fixture
    inputs:
      query: "How to handle IVR routing?"
      language: en
    ground_truth:
      - ref: topics                     # resolved from ground_truth/sources.yaml
        mode: live
      - ref: kb_base
        mode: fixture
        file: fixtures/kb_base.json

  - id: coaching_article
    description: "Agent coaching best practices"
    mode: fixture
    inputs:
      query: "Best practices for agent coaching?"
    ground_truth:
      - ref: topics
        mode: fixture
        file: fixtures/topics_coaching.json
```

### 3.3 Ground Truth Sources

Defined in `ground_truth/sources.yaml`. Five provider types — any scenario can mix them.

```yaml
sources:

  topics:
    type: rest
    swagger: swagger/topics-api.yaml
    endpoint: /v1/topics
    method: GET
    auth: bearer_token
    response_path: $.topics[*]          # JSONPath to extract

  kb_articles:
    type: sql
    connection: "{{env.DB_CONNECTION_STRING}}"
    query: >
      SELECT id, title, content, tags
      FROM kb_articles
      WHERE active = true
      AND category = '{{scenario.inputs.category}}'

  customer_history:
    type: dynamodb
    table: customer-interaction-history
    region: "{{env.AWS_REGION}}"
    key: customerId
    value: "{{scenario.inputs.customerId}}"

  reference_answers:
    type: static
    file: fixtures/reference_answers.json

  # For scenarios with no context needed (mail generation, etc.)
  none:
    type: null
```

Provider types: `rest` | `sql` | `dynamodb` | `static` | `null`

### 3.4 Three-Layer Rule System

Rules are classified into three layers based on how they evaluate output:

| Layer | Type | How it checks | Speed |
|---|---|---|---|
| Layer 1 | Deterministic | Regex, counts, banlist, format, citations | ~1 sec |
| Layer 2 | LLM-as-Judge | Semantic scoring via Bedrock / OpenAI / Azure | ~10–30 sec |
| Layer 3 | RAGAS Metrics | Faithfulness, relevancy, context precision | ~15–45 sec |

### 3.5 Generated Layers YAML

The output of the Rule Generation Agent. Saved to `generated/layers.yaml`. This is the **first-class, reviewable artifact** — committed to git, editable, re-runnable without regenerating.

Each rule entry includes:
- `id` — unique rule identifier
- `source_ac` — the exact acceptance criterion that generated this rule
- `type` — rule type from the built-in catalog
- `field` — JSONPath to the response field under evaluation
- `ground_truth` — which sources to pass as context
- `severity` — `critical | high | medium | low`
- Layer-specific parameters (threshold, phrases, min/max, etc.)

### 3.6 Overrides

Human edits that survive regeneration live in `overrides/layers_override.yaml`. When the agent regenerates `layers.yaml`, overrides are merged on top after generation. This means:
- Teams can tune phrase lists, thresholds, or add custom rules
- Overrides are never lost when the epic is updated and rules are re-generated
- The diff between `generated/` and `overrides/` shows exactly what humans changed

## 4. Rule Generation Agent

### 4.1 Inputs

The agent receives all of the following in a single prompt:

1. **Epic markdown** — acceptance criteria in plain language
2. **Swagger response schema** — field names, types, nesting, required/optional flags
3. **Test case definitions** — input examples, expected behaviors described in text
4. **Rule catalog** — all available rule types with descriptions and parameter signatures

### 4.2 Classification Logic

For each acceptance criterion line in the epic, the agent determines:

```
Can this be checked with a regex, count, phrase scan, or arithmetic?
  → Layer 1 (deterministic)

Does this require reading and semantically judging the output?
  → Layer 2 (LLM-as-judge)

Does this measure context adherence, answer relevancy, or recall?
  → Layer 3 (RAGAS)
```

Severity is derived from AC language:
- "must" / "required" → `high`
- "should" / "recommended" → `medium`
- "may" / "preferred" → `low`
- "no hallucination" / "never" → `critical`

### 4.3 Phrase List Generation

For banlist-type rules (no hedging, no prescriptive language), the agent generates an initial phrase list from the AC context. Human teams extend these in `overrides/layers_override.yaml`.

### 4.4 Execution Modes

| Mode | Command | Behavior |
|---|---|---|
| Dry-run | `llmeval generate --pack <name> --dry-run` | Generates `layers.yaml`, prints it, exits. Human reviews before running. |
| Generate + Run | `llmeval generate --pack <name> --run` | Generates then immediately executes. |
| Run only | `llmeval run --pack <name>` | Uses existing `layers.yaml`. No regeneration. |

### 4.5 Agent Prompt Location

`core/agent/prompts/generate_layers.txt` — the system prompt that instructs the agent how to classify rules, what rule types exist, and what output format to produce. Versioned alongside the framework.

## 5. Scenario Runner

Executes one scenario end-to-end:

```
1. Load scenario (inputs, ground truth refs, mode)
        │
2. Resolve ground truth (parallel)
   ├── RESTProvider.fetch(topics)
   ├── SQLProvider.fetch(kb_articles)
   └── DynamoDBProvider.fetch(customer_history)
        │
3. Call target API
   └── SwaggerClient.call(endpoint, inputs, auth)
       → raw JSON response
        │
4. Extract fields
   └── JSONPathExtractor.extract(response, field_paths_from_layers)
       → flat dict: {field_path → value}
        │
5. Run Rule Engine
   └── RuleEngine.run(layers, extracted_fields, ground_truth_context)
       → list[EvalResult]
        │
6. Report
   └── Reporter.emit(results, scenario_id)
```

### Capture Mode

```bash
llmeval run --pack knowledge-article --capture
```

Runs live, saves all API responses (target + ground truth) to `ground_truth/fixtures/captured/YYYY-MM-DD/`. Future runs can reference these fixtures for deterministic replay.

## 6. Rule Engine

### 6.1 Base Interface

```python
class BaseRule(ABC):
    id: str
    field: str
    severity: Literal["critical", "high", "medium", "low"]

    @abstractmethod
    def evaluate(
        self,
        value: Any,
        context: dict,           # resolved ground truth data
        scenario_inputs: dict    # original test inputs
    ) -> EvalResult: ...

@dataclass
class EvalResult:
    rule_id: str
    passed: bool
    score: float | None          # for LLM judge / RAGAS rules
    explanation: str
    severity: str
    layer: Literal[1, 2, 3]
    duration_ms: int
    source_ac: str               # traceability back to the epic
```

### 6.2 Layer 1 — Built-in Rule Catalog

| Rule Type | Key Parameters | Description |
|---|---|---|
| `word_count_range` | field, min, max | Word count within bounds |
| `sentence_count_range` | field, min, max | Sentence count within bounds |
| `no_phrases` | field, phrases[] | Any phrase from list → fail |
| `required_phrases` | field, phrases[] | At least one must appear |
| `starts_with_word_from` | field, word_list[] | First word must be in list |
| `sentence_case` | field, acronym_whitelist[] | Proper sentence casing |
| `field_citation` | field, source_field, ground_truth | Target field must reference a value from source |
| `regex_match` | field, pattern | Field must match pattern |
| `field_not_empty` | field | Field must be present and non-empty |
| `numeric_threshold` | field, operator, value | Numeric comparison (gt/gte/lt/lte/eq) |
| `count_range` | field (array), min, max | Array length check |
| `no_ordinals` | field | No 1st / 2nd / 3rd language |
| `ordering_check` | field, order_by, direction | Array sorted by key |
| `no_duplicate_values` | field (array), key | No repeated values across array items |

### 6.3 Layer 2 — LLM-as-Judge Rule Catalog

| Rule Type | Key Parameters | Description |
|---|---|---|
| `factual_grounding` | field, ground_truth, model, threshold | Score 0–5: how grounded in source truth |
| `hallucination_check` | field, ground_truth, model | Binary — any hallucination = critical fail |
| `actionability_check` | field, model, threshold | Score 0–5: practical value |
| `tone_check` | field, criteria, model, threshold | Score 0–5 against tone criteria |
| `custom_criteria` | field, criteria, model, threshold | Any natural language criteria prompt |

All Layer 2 rules call `ModelRouter.get_model(model_id)` — no direct Bedrock/OpenAI dependency inside the rule class.

### 6.4 Layer 3 — RAGAS Rule Catalog

| Rule Type | Key Parameters | Threshold Default |
|---|---|---|
| `ragas_faithfulness` | field, ground_truth | 0.75 |
| `ragas_answer_relevancy` | field, question | 0.80 |
| `ragas_context_precision` | field, ground_truth | 0.70 |
| `ragas_context_recall` | field, ground_truth | 0.70 |

RAGAS is configured with a custom LangChain + Bedrock adapter. Embeddings via `sentence-transformers`.

### 6.5 Custom Rules

Teams needing rules beyond the built-in catalog create a Python class in their pack's `custom_rules/` folder:

```python
# eval-packs/knowledge-article/custom_rules/no_jargon.py
from llmeval.rules.base import BaseRule, EvalResult

class NoJargonRule(BaseRule):
    jargon_list: list[str]

    def evaluate(self, value, context, scenario_inputs) -> EvalResult:
        found = [w for w in self.jargon_list if w.lower() in value.lower()]
        passed = len(found) == 0
        return EvalResult(
            rule_id=self.id,
            passed=passed,
            score=None,
            explanation=f"Found jargon: {found}" if found else "Clean",
            severity=self.severity,
            layer=1,
            duration_ms=0,
            source_ac=self.source_ac
        )
```

Referenced in `overrides/layers_override.yaml`:
```yaml
layer1:
  - id: no_jargon
    type: custom:no_jargon.NoJargonRule
    field: response.article.content
    jargon_list: ["synergize", "leverage", "paradigm shift"]
    severity: low
```

Override merge rules:
- If `id` matches a rule in `generated/layers.yaml` → the override replaces that rule's parameters entirely
- If `id` does not exist in generated → the override is appended as a new rule
- Overrides are applied at runtime, not written back into `generated/layers.yaml`

## 7. Model Router

Decouples all LLM judge rules from specific providers. Every Layer 2 call routes through `ModelRouter`.

### 7.1 Interface

```python
class BaseLLM(ABC):
    def complete(self, messages: list[dict], max_tokens: int) -> str: ...

class ModelRouter:
    def get_model(self, model_id: str) -> BaseLLM: ...
    def compare(
        self,
        prompt: str,
        models: list[str]
    ) -> dict[str, str]: ...   # model_id → response
```

### 7.2 Implementations

| Class | Provider | Auth |
|---|---|---|
| `BedrockLLM` | AWS Bedrock | `AWS_PROFILE` / IAM role |
| `OpenAILLM` | OpenAI | `OPENAI_API_KEY` env var |
| `AzureOpenAILLM` | Azure-hosted OpenAI | `AZURE_OPENAI_*` env vars |
| `OllamaLLM` | Local via Ollama | No auth — local endpoint |

### 7.3 models.yaml

```yaml
layer2:
  default_model: claude-sonnet-4-6
  provider: bedrock
  region: us-east-1

layer3:
  llm_model: claude-sonnet-4-6
  provider: bedrock
  embeddings: sentence-transformers/all-mpnet-base-v2

comparison_mode:
  enabled: false
  models:
    - id: claude-sonnet-4-6
      provider: bedrock
    - id: gpt-4o
      provider: openai
      api_key_env: OPENAI_API_KEY
    - id: claude-haiku-4-5
      provider: bedrock
```

### 7.4 Comparison Mode

When `comparison_mode.enabled: true`, every LLM judge rule runs against all configured models. Results include per-model scores. Used to calibrate which judge model performs best for a given domain — not for everyday CI runs.

## 8. CLI

Entry point: `llmeval` (installed via `pip install llm-eval-framework`)

```bash
# Generate rules from epic + swagger + testcases
llmeval generate --pack eval-packs/knowledge-article

# Dry-run: inspect generated layers.yaml before executing
llmeval generate --pack eval-packs/knowledge-article --dry-run

# Generate then immediately run
llmeval generate --pack eval-packs/knowledge-article --run

# Run with existing layers.yaml (no regeneration)
llmeval run --pack eval-packs/knowledge-article

# Run specific scenarios
llmeval run --pack eval-packs/knowledge-article --scenario routing_article

# Run specific layers only
llmeval run --pack eval-packs/knowledge-article --layers 1,2

# Capture live responses as fixtures
llmeval run --pack eval-packs/knowledge-article --capture

# Compare judge models
llmeval run --pack eval-packs/knowledge-article --compare-models

# Run all packs (CI mode)
llmeval run --all eval-packs/ --output report.html --format html

# Validate pack structure (no API calls)
llmeval validate --pack eval-packs/knowledge-article
```

## 10. Migration from csa-llm-evaluation

The existing `csa-llm-evaluation` rules (S1–S16, R1–R16) map directly to the generic rule types:

| Old Rule | New Rule Type | Layer |
|---|---|---|
| S2 count accuracy | `field_citation` + `numeric_threshold` | 1 |
| S3 insights count | `count_range` | 1 |
| S4 topic citation | `field_citation` | 1 |
| S6–S11 banlists | `no_phrases` | 1 |
| S12 sentence case | `sentence_case` | 1 |
| S13 empty data | `field_not_empty` | 1 |
| R1 rec count | `count_range` | 1 |
| R2 title verb | `starts_with_word_from` | 1 |
| R9 ordering | `ordering_check` | 1 |
| E2.1 factual grounding | `factual_grounding` | 2 |
| E2.3 hallucination | `hallucination_check` | 2 |
| E2.4 RAGAS faithfulness | `ragas_faithfulness` | 3 |
| E2.5 RAGAS relevancy | `ragas_answer_relevancy` | 3 |

Migration path: create an eval pack for the existing CXOne agentic analytics domain pointing to the existing Swagger specs. The existing epics and test cases are written once; the agent generates the layer config.

## 11. Open Questions

1. **Pack registry** — Should packs be publishable to a shared registry (e.g. internal PyPI / S3 bucket) so teams can inherit common rule packs without copying them?
2. **Auth abstraction** — Bearer token works for REST ground truth sources. Should SQL and DynamoDB credentials use a vault integration (AWS Secrets Manager / HashiCorp Vault)?
3. **Async execution** — Should Layer 2 and Layer 3 rules run concurrently within a scenario to reduce wall-clock time?
4. **Deployment model** — Library (pip install) vs shared service vs template repo — deferred, to be decided after initial library is built.

## 12. Acceptance Criteria for the Framework Itself

- [ ] A QA engineer with a Swagger doc + epic markdown can run their first evaluation with zero Python code changes
- [ ] `llmeval generate --dry-run` produces a `layers.yaml` where every rule has a `source_ac` tracing back to an epic line
- [ ] Ground truth providers for REST, SQL, DynamoDB, static, and null all work independently
- [ ] Overrides in `layers_override.yaml` survive a `llmeval generate` re-run
- [ ] Layer 1 rules complete in under 5 seconds per scenario
- [ ] Comparison mode produces a side-by-side score table across configured models
- [ ] All existing csa-llm-evaluation use cases (S1–S16, R1–R16, E2.1–E2.5) can be expressed as eval packs
